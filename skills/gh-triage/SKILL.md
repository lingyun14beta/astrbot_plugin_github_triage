# GitHub 审阅助手

把一条新 issue / PR 变成**一条可直接发布的评论草稿**。核查过程留在内部，对外只给评论。

本说明书**不带仓库专有知识**：issue 模板必填字段、标签口径、日志格式、构建与测试命令，都写在该仓库对应的格式 / 规范 skill 里（例如 `gh-issue-format`、`gh-code-review`）。这里只管流程。

## 开始前先确认三件事

1. **目标仓库**：`owner/repo`。抓取一律用上游 slug —— 本地 `origin` 可能是 fork，用 fork 抓会 404 或漏评论。
2. **本地仓库路径**：只在「需要读代码定位」或「需要跑 lint / 测试」时才要。用户没给就问；拿不到就降级为静态审查，并在评论里写明。
3. **条目编号**：从通知里取，或由用户给出；编号属于 issue 还是 PR 决定走哪条工作流。

先读该仓库的规范文件（`CONTRIBUTING`、`AGENTS.md`、`Makefile`、CI 配置）——后面每一条结论都要对齐它的约定。

## 工作流 A：issue

1. **判类型**：bug / feature / 性能 / 文档 / 使用咨询 / 第三方归属。依据是**该仓库自己的**标签体系与 issue 模板小标题，不是通用套路。
2. **取原文**：正文与评论原样保留，不改写；同时标出模板里的空字段（未填字段常渲染成 `_No response_`）—— 这些才是可能要追问的信息。
3. **bug 找根因**：
   - 先排除三类非本仓库问题：第三方插件 / 扩展、环境与部署问题（容器、代理、编码、平台策略）、报告版本低于当前代码且已修 → 直接给「升级到 X」。
   - 用**报告者给的原始证据**钉代码位置：日志、堆栈、异常类型、配置键、报错文案。若该仓库的日志自带 `文件:行号`，那就是最快的定位入口；命中后读整个函数与相邻代码，沿调用链回溯到触发入口，并写清触发条件。
   - 行号会随版本漂移：引用前先确认与报告版本是否一致，用 `git log -S"<文案>"` 或 `git log -L` 对齐，并在结论里带上版本锚点。
   - 定位不到就给 2–3 个候选 + 各自验证方法 + 缺失的证据，不要硬下结论。
4. **feature 看需求面**：先问「能不能不改代码就满足」——现有配置项、插件 / 扩展机制、命令、脚本、提示词配置；再核对是否已实现或已有相关 PR。
5. 用**该仓库的评论格式 skill** 产出评论（没有就用 `gh-code-review` 的通用原则 + 仓库既有评论风格）。

## 工作流 B：PR

1. **抓全**：元数据、改动文件、提交列表、完整 diff。读作者自己写的描述与勾选项，**再用 diff 核对**（「不破坏兼容」「已测试」「没加依赖」是否属实）。作者声明与 diff 不符，这件事本身就要写进结论。
2. **本地还原**（需要核查代码时）：用独立 worktree，**绝不改动用户工作区**
   ```
   git fetch <承载该 PR 的 remote> pull/<n>/head:pr-<n>
   git worktree add <仓库外的目录> pr-<n>
   ```
   先 `git remote -v` 确认哪个 remote 承载该 PR（可能是 `origin`，也可能是 `upstream`）。还原不了就明说「未在本地还原改动」。
3. **验证**：跑该仓库自己的检查命令（从 `Makefile` / CI 配置 / `CONTRIBUTING` 里找），只跑与改动相关的，别盲目全量
   ```
   <lint 命令>            # 例：ruff check . / npm run lint
   <格式化检查>           # 例：ruff format --check . / prettier --check
   <相关测试>             # 例：pytest tests/xxx.py -q / npm test -- xxx
   ```
   注意工具版本要对齐 CI（本地工具版本不同会产生假报警）。跑过的不用写进评论；没跑或只跑一部分，就在评论里补半句。
4. **按改动面挑参考**：`gh-code-review` 里有分语言 / 分领域的审查清单（Python、Vue、TS、安全、性能、架构……），**按改动内容挑，不要全读**。
5. 用**该仓库的评论格式 skill** 产出评论；没有就按 `gh-code-review` 的通用格式（结论 + 分级问题 + `文件:行号`）。

## 硬性规矩

- **不自动发布**：默认只把草稿发回会话；听到明确的「发」才发布。没有明确授权就只能 dry-run。
- 不点批准、不合并、不打标签、不关闭 issue/PR；不写「我批准合并」这类冒充维护者的话。
- 每条问题必须带 `文件:行号`；没证据的降级或删掉，**不为填满模板硬凑条目**。
- **禁绝对措辞**：完全 / 都 / 一定 / 所有 / 必然 / 从不 → 换成 未发现 / 未见 / 仅 / 目前 / 在已核查范围内 / 该路径未覆盖。
- 结论与级别联动：出现阻断级（🔴 或 P0）才写「需修改」，否则写「可合并」。
- 不把 token、密钥、cookie、个人隐私写进评论或日志。
- 评论语言跟随原贴语言；末尾保留 AI 声明（该仓库若另有声明惯例，遵循它）。
- 权限现实：**非协作者**提交的正式 review（`REQUEST_CHANGES`）不会计入合并门槛，需要「真的拦住」时要提醒用户。

## 交回会话的草稿长什么样

1. 一句结论（可发 / 需修改，以及最关键的那条理由）
2. 评论正文（完整、可直接粘贴）
3. 末行交代：目标仓库与编号、当前是草稿还是已发布、发布后的链接

## 失败与降级

- **限流**：匿名 60 次/小时（按出口 IP），带 token 5000 次/小时。受限时改用网页抓取、走不同出口，或让用户提供 token。
- **无法还原改动**：只做静态审查，并在评论里写明。
- **测试跑不起来**：写明「未执行测试」，不要声称跑过。
- **找不到仓库规范**：按通用最佳实践审查，并在结论里说明依据来自通用实践而非该仓库约定。
