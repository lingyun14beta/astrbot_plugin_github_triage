# issue 评论格式

交付物是**一条可直接发布的评论**，不是长报告。核查过程不写进来。

## 先判类型再选模板

| 类型 | 判定依据 |
| --- | --- |
| bug | 标签 `bug`、标题 `[Bug]`、模板小标题 `### 问题描述` |
| feature | 标签 `enhancement`、标题 `[Feature]`、模板小标题 `### 功能描述` / `### 使用场景` |
| 其他 | 性能 / 文档 / 使用咨询 / 插件归属 → 见文末 |

## bug 模板

```markdown
**结论**：<本体 bug / 插件问题 / 环境问题 / 已在 X 版本修复 / 信息不足>
**根因**：<一句话> —— `<file>:<line> @ <短SHA>`
**建议**：<最小修复方向>
**建议标签**：`area:core`
```

- 基础 4 行；**只有**确实缺必填字段时才追加 `**需要补充的信息**：…`
- 不写「证据」「复现」两行 —— 关键证据压进「根因」那一行，复现过程留在内部
- 未实机复现时，在「根因」末尾标注「（静态定位，未实机复现）」
- 行号必须带版本：`<file>:<line> @ <短SHA>`
- bug **不给** `feature:*`

## feature 模板

```markdown
**需求本质**：<要解决什么场景或痛点；不复述他提的方案>
**现状**：<只讲当前行为；不写文件路径与行号>
**受益规模**：<哪类部署会受益>
**建议标签**：`area:core` `feature:plugin`
```

- 基础 4 行；**只有**存在真正的不定点时才追加 `**可能需要讨论的点**：…`（用陈述句，不要写成对报告者的提问）
- feature 评论**不出现** `文件:行号` —— 代码细节留在内部
- 标签用 `area:*` + `feature:*`

## 建议标签口径

`area:*`（可多选，通常都能给出）

| 标签 | 覆盖范围 |
| --- | --- |
| `area:core` | 核心与后端 |
| `area:platform` | IM 平台适配器 |
| `area:provider` | Provider / 模型 / Agent |
| `area:webui` | dashboard |

`feature:*`（**仅 feature request**，可多选）：`feature:chatui`、`feature:knowledge-base`、`feature:persona`、`feature:plugin`、`feature:updater`

`priority:*`（可选，**标签名带空格**）

| 标签 | 判据 |
| --- | --- |
| `priority: p0` | 安全或数据风险，或阻塞核心流程 |
| `priority: p1` | 影响多用户，且没有现成绕行方案 |
| `priority: p2` | 影响特定场景，或已有绕行方案 |
| `priority: p3` | 小众需求、体验优化 |

规则：只列**建议新增**的标签（与 issue 已有标签一致就跳过）；用反引号包住准确名称；这是建议不是决定，不写命令口吻。没有可建议的就省略整行。

## 其他类型

- **性能**：量化结果 + 热路径定位 + 优化建议
- **文档**：应更新的位置 + 具体改写点
- **使用咨询**：直接答案 + 依据（配置键 / `文件:行号`）
- **插件**：归属判定 + 证据，不按本体 bug 深挖
- **类型不明**：先确认是缺陷、功能建议还是咨询，再决定流程

## 最后

语言跟随 issue 语言；末尾保留 AI 声明。
